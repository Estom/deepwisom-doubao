# AtomStudio 原子工作室 — 开发流程文档

> 本文档记录 AtomStudio（多智能体 AI 应用生成平台 Demo）从需求到上线的完整开发流程、工程结构与协作规范，供后续迭代、复现与交接使用。

---

## 1. 项目简介

- **产品名称**：AtomStudio 原子工作室
- **产品定位**：对标 [Atoms（atoms.dev，原 MetaGPT/MGX）](https://atoms.dev) 的多智能体 AI 应用生成平台 Demo
- **核心能力**：用户用自然语言描述需求，多个角色化智能体按软件研发 SOP 流水线协作（需求分析 → 架构设计 → 代码生成），在数分钟内产出可运行的单文件 HTML 网页应用，并支持实时预览、代码复制/导出、任务清单、版本历史与回滚
- **界面语言**：中文（zh-CN）
- **视觉风格**：深色科技风，紫蓝渐变高亮 + 彩色智能体头像

### 智能体团队与协作流水线

| 智能体 | 角色 | 主题色 | 职责 |
|---|---|---|---|
| Mike | 团队领队 | 暖橙 #FF8A3D | 接单概述、协调流程、总结交付 |
| Emma | 产品经理 | 粉紫 #E879F9 | 拆解需求为功能列表与用户流程 |
| Bob | 架构师 | 蓝白 #60A5FA | 设计页面结构、拆分任务 |
| Alex | 工程师 | 蓝色 #3B82F6 | 生成完整自包含单文件 HTML 代码 |
| David | 数据分析师 | 绿色 #34D399 | 数据类应用的数据结构与指标建议（可选） |

**流水线顺序**：Mike（接单概述）→ Emma（需求分析）→ Bob（架构设计）→ Alex（代码生成）→ Mike（总结交付）；数据类需求由 David 可选参与。

## 2. 技术栈

### 前端框架与语言

- React 19 + TypeScript 5.9
- Vite 8（构建与本地开发）
- Tailwind CSS 4 + `@tailwindcss/typography`、tw-animate-css
- shadcn/ui 组件体系（基于 Radix UI，组件位于 `src/components/ui/`）
- React Router DOM 7（路由）

### 关键依赖

| 用途 | 依赖 |
|---|---|
| 动画 | framer-motion、gsap / @gsap/react、@formkit/auto-animate |
| Markdown 渲染 | react-markdown + remark-gfm |
| 图表 | echarts / echarts-for-react、recharts |
| 工具库 | date-fns、lucide-react、zod、react-hook-form |
| 提示反馈 | sonner |
| 平台运行时 | @lark-apaas/client-toolkit-lite（scopedStorage 等） |
| 平台工程预设 | @lark-apaas/coding-presets-react、@lark-apaas/coding-preset-vite-react |

### AI 能力插件

- `@official-plugins/ai-text-generate` 1.0.21（平台运行时插件）
- 5 个智能体各自对应一个 capability 实例，定义在 `shared/capabilities/`：
  - `team_leader_mike_text_generate_1`
  - `pm_emm_product_requirement_generate_1`
  - `architect_bob_text_generate_1`
  - `alex_eng_html_code_generator_1`
  - `data_analyst_david_text_generate_1`

> **铁律**：多智能体生成功能必须走真实插件（real-plugin），严禁用 mock 文本冒充 AI 生成结果。

## 3. 开发环境准备

1. 安装 Node.js（建议 18+）与 npm
2. 克隆仓库后安装依赖：

   ```bash
   npm install
   ```

3. 平台私有依赖（`@lark-apaas/*`）与运行时插件需在妙搭/托管平台环境内才能完整获取与运行，详见第 9 节「已知限制」。

## 4. 开发流程总览

```text
需求分析 → 竞品调研 → 产品设计（页面/数据/智能体） → 能力与插件配置
        → 页面与业务编码 → 静态检查与构建验证 → 平台部署上线
        → 源码导出本地 → Git 初始化与推送 → 迭代维护
```

### 4.1 需求分析

- 通读笔试/需求文档，提炼硬性要求：真实交互、数据持久化、注册登录与核心主流程、至少一个延展能力、提供公开可测试的在线链接
- 明确交付物：可在线访问的网站 + 平台工程源码 + 说明文档

### 4.2 竞品调研

- 调研 Atoms（原 MGX）的产品形态：多角色智能体团队、SOP 流水线、即时预览、任务清单、版本分支回滚、代码导出、模板库
- 输出可落地的功能清单与页面规划，区分核心功能与延展功能

### 4.3 产品设计

- **页面规划**：落地页、注册/登录页、项目仪表盘、核心工作台、模板库
- **数据规划**：用户、会话、项目、消息、任务、版本的存储口径
- **智能体设计**：各角色的系统提示词基线、主题色、输出格式约束
- 设计结论沉淀于 `AGENTS.md`（需求拆解 / 数据来源声明 / 角色定义 / 插件铁律）

### 4.4 能力与插件配置

- 在 `shared/capabilities/` 为每个智能体配置 `ai-text-generate` capability（流式输出）
- 在 `package.json` 的 `actionPlugins` 中声明运行时插件版本

### 4.5 编码实现

- 按「入口/路由 → 公共组件 → 业务 hooks/lib → 页面」的顺序实现
- 公共 UI 组件统一放在 `src/components/ui/`，业务组件放在 `src/components/`
- 可复用逻辑收敛到 `src/lib/` 与 `src/hooks/`

### 4.6 验证

- 类型检查：`npm run typecheck`
- Lint：`npm run lint:eslint`（或 `npm run lint` 同时跑类型检查）
- 生产构建：`npm run build`
- 要求 TypeScript 与构建 0 error 后方可交付

### 4.7 部署上线

- 在托管平台内构建并发布，获得公开可访问的在线链接
- jspage 类型产物发布后自动托管，无需额外手动部署

### 4.8 源码导出与 Git

- 将平台工程源码导出到本地仓库
- 初始化 Git、配置远程仓库并推送（见第 8 节）

## 6. 页面与路由

| 页面 | 路由 | 说明 |
|---|---|---|
| 落地页 | `/` | 产品介绍、核心入口 |
| 注册/登录 | `/auth` | 注册、登录、会话建立 |
| 项目仪表盘 | `/dashboard` | 项目列表、新建/进入项目 |
| 核心工作台 | `/workspace/:projectId` | 对话区 + 预览/代码/任务/版本三栏布局 |
| 模板库 | `/templates` | 预置模板卡片 |

工作台为三栏布局：左侧对话区（智能体团队 + 消息流 + 输入框），右侧工作区（预览 / 代码 / 任务清单 / 版本历史四个标签页）。

## 7. 数据持久化

数据通过平台 `@lark-apaas/client-toolkit-lite` 的 scopedStorage 持久化，键前缀统一为 `atomstudio_`：

| 数据 | 存储键 | 说明 |
|---|---|---|
| 会话 | `atomstudio_session` | 当前登录会话 token |
| 用户 | `atomstudio_users` | 用户账户，密码使用 SHA-256（crypto.subtle）哈希存储 |
| 项目 | `atomstudio_projects_{userId}` | 按用户隔离的项目元数据 |
| 消息 | `atomstudio_messages_{projectId}` | 按项目存储的对话记录 |
| 任务 | `atomstudio_tasks_{projectId}` | 架构师拆分的任务清单 |
| 版本 | `atomstudio_versions_{projectId}` | 代码版本快照，支持回滚 |

> 注意：早期规划文档（AGENTS.md）中出现过 `__atomstudio_*` 前缀，**实际代码以 `atomstudio_` 为准**。

## 8. 常用命令与 Git 规范

### 常用命令

```bash
npm run dev          # 启动本地开发（node scripts/dev.mjs）
npm run build        # 生产构建（bash scripts/build.sh）
npm run typecheck    # TypeScript 类型检查
npm run lint:eslint  # ESLint 检查 src
npm run lint         # 类型检查 + ESLint 并发执行
```

### Git 流程

1. 首次初始化：

   ```bash
   git init
   git add .
   git commit -m "feat: AtomStudio 原子工作室 - 多智能体 AI 应用生成平台 Demo"
   git branch -M main
   git remote add origin git@github.com:Estom/deepwisom-doubao.git
   git push -u origin main
   ```

2. 日常迭代：

   ```bash
   git add <files>
   git commit -m "type: 简明描述"
   git push
   ```

3. 提交信息建议使用约定式前缀：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`style`、`refactor`、`chore`。
4. Git pre-commit 钩子（`scripts/setup-git-hooks.mjs`，通过 `npm run prepare` 安装）会在提交前执行 lint。

### .gitignore 要点

- 笔试原题/需求文档（含敏感信息）**禁止入库**，已通过精确文件名与通配规则（如 `*ROOT*笔试*.md`）排除
- 同时忽略 `node_modules/`、构建产物、日志与系统临时文件
- 提交前可用 `git check-ignore <file>` 复核敏感文件是否被忽略

## 9. 已知限制

1. **平台依赖**：工程依赖 `@lark-apaas/*` 私有包与平台运行时插件，脱离托管平台直接 `npm run dev` 未必能完整跑通；源码定位为「平台工程源码」，完整体验以在线版本为准。
2. **生成产物形态**：Alex 生成的是自包含单文件 HTML（内联 CSS/JS、不依赖外部 CDN、数据用 localStorage），平台侧会自动剥离响应中可能出现的 Markdown 代码包裹。
3. **失败兜底**：AI 生成失败时提供错误提示与一键重试；规划阶段失败会自动跳过并直接进入代码生成。

## 10. 迭代与 Bug 修复流程

以「工作台聊天区无法向上滚动」修复为例，标准迭代流程如下：

1. **复现与定位**：阅读 `src/pages/WorkspacePage/WorkspacePage.tsx`，定位消息流容器与自动滚动逻辑。
2. **根因分析**：
   - ScrollArea 作为 flex 子项缺少 `min-h-0`，高度约束不可靠；
   - 自动滚底 effect 依赖 `messages`，流式输出每个 token 都触发 `scrollIntoView`，用户上滚被反复拉回。
3. **修复方案**：
   - 消息区外层与 ScrollArea 补充 `min-h-0`；
   - 通过 `closest('[data-radix-scroll-area-viewport]')` 获取真实滚动视口；
   - 仅在用户位于底部附近（120px 内）时自动滚底；
   - 增加滚动监听与「回到底部」悬浮按钮；用户主动发消息后强制滚到底。
4. **验证**：类型检查与生产构建通过，线上按「发送长需求 → 生成中上滚 → 按钮回底」路径验证。
5. **同步与交付**：线上修复部署后，将改动文件同步回本地，提交 `fix:` 类型 commit 并推送。

### 线上产物修改原则

- 托管平台上的在线产物修改须在平台工程内完成并重新发布；本地源码在修复后及时同步，保证仓库与线上一致。
- 每次迭代结束确认：线上已生效、本地已提交、远程已推送、工作区干净。
